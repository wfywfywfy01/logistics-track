# 销售分摊人员物流通知修复与验收

## 问题和行为

销售订单接口的“销售user_id”返回同一订单的全部参与人 UID，例如 `12537、12542、12549`。此前只保存一个“销售人员”姓名，按订单号后缀汇总子单的方式不能覆盖业务分摊。

预报、面单自动建单、配单和重新匹配现均保存 `sales_recipient_ids`。通知按订单、事件、UID 去重；旧姓名任务和已有 UID 任务继续参与去重。旧通知收件身份无法核实的事件转入待办，禁止绕过 unknown 回执重新发送。主要人员保留原语义，分摊名单不会覆盖人工指定主要人员。

整轮追踪在回填轨迹前同步已入库订单的参与人。活动订单的名单有效期为 24 小时；终态订单完成首次同步后不做例行重查，显式指定订单可以刷新。接口失败不覆盖已核实名单，不写新鲜时间。修复后在人员资料过期或缺失时产生的物流事件带待补齐标记，资料恢复后原子补齐各事件的遗漏私聊任务，避免没有新状态就永远不通知。

## 执行与验收

所有查询沿用服务现有授权。同步不会把其他销售订单自动导入国际物流台账。

```text
python tracking-pipeline.py sync-sales-recipients --order XSD260921144644 --order XSD260830140807
python tracking-pipeline.py sync-sales-recipients --order XSD260921144644 --order XSD260830140807 --apply
python tracking-pipeline.py sync-sales-recipients --order XSD260921144644 --replay-latest --recipient-uid 12537
python tracking-pipeline.py sync-sales-recipients --order XSD260921144644 --replay-latest --recipient-uid 12537 --apply
```

默认是预览。`--apply` 更新人员；只有显式 `--replay-latest` 才补修复前的历史状态，且仅私聊、不重发群消息。`--recipient-uid` 是已有授权收件人名单的筛选，不能添加任意人员。没有状态事件或明确静默的事件不补发。补发正文标注“历史状态补发”。命令只原子入队，由正常通知工作进程发送，不增加第二套发送入口。

验收标准：

1. 两张已核实订单均保存何川 UID `12537`，原主要人员、国际单号、版本、历史不变。
2. 已签收订单产生且只产生一条对应事件的何川私聊任务，得到服务端发送回执。已预报且无国际单的订单只同步参与人，不伪造轨迹事件。
3. 重复执行补发，任务总数和已发消息数不增长；原主要人员已有成功/不明确回执不重发。
4. 并发工作进程按稳定 UID 预留唯一任务；租约过期的进程不能开始发送。
5. 销售查询失败、分页不完整、名单无有效 UID 时保持旧资料；恢复后补齐修复后期间的每个物流事件。
6. 同名多个 UID、无法确定旧任务收件人时生成待办，不自动重发可能已发出的消息。
7. 完整测试及 Linux CI 通过，新发布 SHA 和 `/healthz` 一致；发布前备份和旧容器可回滚。

测试使用模拟销售/IM 响应。生产验收以数据库任务、唯一事件键、UID、发送回执中的消息 ID 为证据；`succeeded` 不等于用户已读。回滚恢复旧代码容器，保留当前数据卷，不覆盖补发后的回执数据库。
