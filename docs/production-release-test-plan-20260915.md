## 上线前输入

开始隔离候选测试前必须确定：

1. 专用测试群、测试机器人和至少两个测试用户，不能向正式业务群发送测试通知。
2. UPS、DHL、FedEx 各至少5条授权查询的有效运单；覆盖在途、异常、签收，无法提供的状态明确记录。
3. UPS、DHL、FedEx 停滞阈值和官网数据最大有效期，由运营负责人确认。
4. 后台访问域名或 VPN 入口、TLS 证书方案、可信反向代理地址。
5. Docker 管理面允许来源和替代管理通道；收紧2375前必须验证新通道。
6. 异地备份目标、凭据、RPO和RTO负责人。建议门槛：RPO≤1小时、RTO≤2小时。

任一输入缺失时，对应能力保持“未验收”，不能写成生产可用。

## 第二层：隔离候选测试

使用生产数据库和附件卷的一致性副本，独立命名卷、独立端口、专用通知渠道。先记录订单数、任务数、附件数、数据库哈希及 `integrity_check`。测试后销毁候选副本，不反写生产。

部署前先检查现有容器的 `Mounts`。当前服务应继续挂载既有 `logistics-data`、`logistics-tmp`、`logistics-backups` 卷；如果旧环境仍使用仓库目录 bind mount，必须停写、备份、复制到命名卷并核对订单数、附件数和 `integrity_check`，禁止直接启动空卷。

### 数据与换单

| 场景 | 验证 | 通过标准 |
| --- | --- | --- |
| 重复预报 | 同订单重复导入，期间已有绑定、轨迹、通知回执 | 绑定版本、历史、当前轨迹和回执不丢；冲突进入审核 |
| 并发更新 | 两订单并发写入；同包裹新旧观测交错 | 其他订单字段不丢；旧观测和旧绑定结果被拒绝 |
| 签收后换单 | 已签收包裹换成新运单 | 订单立即回到待跟踪；旧轨迹只在绑定历史；新轨迹无旧观测 |
| 重复运单换入 | 换成同订单已有运单 | 请求失败，订单、包裹和审计均不改变 |
| 审计故障 | 注入审计写失败 | 包裹变更整体回滚 |

### 通知

| 故障点 | 通过标准 |
| --- | --- |
| 发送前参数、人员解析或明确拒绝失败 | 保持可重试；未写成功回执 |
| 发送超时、空回执、未知回执 | 任务进入 unknown，不自动重发 |
| CLI 非零退出但没有结构化明确拒绝 | 任务进入 unknown；只有 `ok=false` 才自动重试 |
| 对端成功后本地回执写入失败 | 任务进入 unknown，后续接管不重发 |
| 状态发送期间又产生新状态 | 旧回执不清除新状态通知标记 |
| 人工确认 unknown | 当前事件才允许确认；操作者和原因有审计 |
| 异常、恢复、再次异常 | 每个真实事件各通知一次；异常消息带警告标识 |

核账：任务 dedupe_key、发送回执、订单事件标识和审计一一对应。任何重复发送或无任务记录的直接发送均失败。

### 调度、批次与接管

- 在09:05或15:05占用全局锁；任务不能写成功标记，释放后必须补跑一次。
- 在定时点停机，稍后启动；当天未完成任务必须补跑。
- 注入一个抓取线程写库异常；批次退出非0，expected、completed、failed相符。
- 批次中断后重跑；成功结果幂等，旧结果不能覆盖新观测。
- watcher、后台服务、代理分别退出；健康检查和容器重启行为符合预期。

### 停滞和数据过期

- 同为“运输中”但出现新扫描：不产生停滞任务。
- 多包裹中仅一个超过其承运商阈值：只标记该包裹。
- 官网抓取失败、结果过期、物流无新扫描分别生成不同原因。
- 缺时间或阈值：显示 N/A，并阻断停滞结论。

### 后台安全

- admin、operator、viewer 权限矩阵、越权请求、CSRF、退出、密码修改后会话失效。
- Content-Length 为负数、非法值、超过65536字节均拒绝。
- 慢请求超过15秒被断开；并发连接超过64时服务保持可用。
- 只通过服务器本机端口或受控代理访问；HTTPS入口启用 Secure Cookie。后端端口不可从非授权网络直连。

## 第三层：备份与恢复

1. 在候选副本制造 pending、running、dead 附件，以及被未结审核引用的 succeeded 附件各一份，执行备份。
2. 校验压缩包中数据库、manifest和每个受保护附件的 SHA-256。
3. 在空数据卷和空附件卷恢复；验证订单数、任务数、附件内容和后台原件链接；注入附件切换失败并确认数据库与已覆盖附件完整回滚。
4. 篡改数据库和附件各一次，恢复必须拒绝。
5. 在恢复后继续一轮 OCR、官网查询、台账回填和通知测试。
6. 上传异地主机或对象存储，再从异地副本重复恢复。

验收：所有受保护附件可读，数据库 `integrity_check=ok`，实测 RPO/RTO满足确认目标。只有同机备份时，异地容灾不得判通过。

## 第四层：官网真实样本

对三家每条样本保存查询时间、来源、官网截图或人工对照记录；运单号在报告中脱敏。

逐项核对：官网状态、内部阶段、预计送达、最后位置、最新事件、事件总数、每条事件时间/地点/描述、进度节点可用性、异常或报关标识。官网未提供字段应为 N/A，不能以推断值充当官网事实。

验收指标：

- 状态查询成功率≥98%。分母包含超时、解析失败和反爬失败；官网明确无单独立统计。
- 官网存在完整历史时，系统完整事件覆盖率≥95%，事件数量和关键字段与官网一致。
- FedEx 至少一条有效实票完成端到端；未完成时 FedEx 保持“试验能力”。
- 官网降级或临时失败时保留最近一次官方详情，并明确显示抓取时间和过期状态。

## 第五层：灰度生产

发布前创建带附件的完整备份并完成校验；保留旧镜像和旧容器配置。候选先接测试渠道运行，再切正式入口。灰度观察72小时：

- 每30分钟记录 watcher、调度、抓取、回填、通知、备份各自最后成功时间。
- 每日核对 expected/completed/failed、订单增量、任务状态、附件状态和通知回执。
- dead、unknown、review和 tracking_failure 的新增量必须能解释；未知积压不得持续增长。
- 容器无 OOM、无异常重启；数据库完整性正常；磁盘、内存、共享内存有余量。
- 抽样订单与官网、原始面单、群通知和录单人私聊形成闭环。

## 立即回滚条件

发生任一情况停止新任务并回滚：订单或绑定历史丢失、重复业务通知、旧状态覆盖新状态、数据库完整性失败、生产数据卷不匹配、附件无法恢复、管理权限绕过、连续两个应执行批次未完成。

回滚顺序：停止候选入口，保全当前数据库和附件快照，使用记录的旧镜像及同一命名卷恢复服务；不得用旧数据库覆盖切换后新数据。回滚后核对新增订单和待办，再决定前向修复或数据合并。
